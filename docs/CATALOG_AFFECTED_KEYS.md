# 仅重算受影响域名：隔离实验

`3090b64` 的合并投影读端仍比现有业务冷摘要慢。这次不再调整全量 SQL，改为验证一件事：**已知行级变更时，能否只修复受影响域名的贡献，并保留其余结果？**

内存实验位于 `tests/prototypes/affected-catalog.ts`，用 `npm run test:prototype:catalog` 运行。未接入生产，也未增加 SQL 表、任务、缓存格式或写入钩子。

## 修复范围

| 变更 | 必须重算 |
|---|---|
| 改名或换来源 | 旧、新归一化域名；保留其他来源并重新选赢家 |
| 删除到期或注册赢家 | 同域剩余来源；没有来源才移除域名 |
| 更新或删除已解析的日期覆盖 | 反向依赖中所有引用该日期键的域名；剥离不可见字符后的查询键不是去重键 |

初始构建仍需读取全部输入。内存中同时保留来源行、归一化键索引和日期候选反向索引。并列顺序保留 `(来源顺序, 库存 ID)`，不使用改动后会重新编号的全局位置；托管与自定义的相同 ID 不互相覆盖。覆盖变更与改名同批时，按变更后的来源和日期查找。

## 验证结果

- 50,000 条独立模拟库存中，改名单个域名标记 2 个键，访问 2 条成员记录（含移出的旧行和加入的新行）；更改单个日期键，访问 1 条反向依赖和 1 条来源。**这是内存记录访问次数，不是 D1 扫描行数或耗时。**
- 64 批混合改名、删除、换来源和覆盖变更逐批与完整重建的贡献一致。另用现有摘要核对替换来源前后的到期赢家、首次注册及严格的到期毫秒边界。
- 反向依赖过大或某域来源过多时，整批拒绝；不发布部分结果，也不推进实验序号。重复行变更、重复日期键、过期序号及无法保证等价的极端日期也拒绝。这里的原子性仅是一次同步内存更新，不是数据库事务或崩溃恢复。

## 仍待解决

实验假定调用者提交**完整且顺序正确**的行变更，并已将手动覆盖/RDAP 解析为有效日期映射。它不捕获线上事务、级联删除或旧版本直接写入，不维护 RDAP 自然过期任务，也不增量维护全局计数、月桶与有限结果。完整对照快照仍会遍历库存。本批不测生产 CPU、峰值内存或费用，也不改变非法日期的显示规则。

下一步若继续，应先测「可靠变更捕获＋来源／日期依赖持久索引」的写入放大，特别是批量同步、删除及覆盖失效。现有生产摘要仍是默认方案。
