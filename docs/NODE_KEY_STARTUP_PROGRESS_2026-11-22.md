# Node 密钥与启动就绪安全（2026-11-22）

承接摘要缓存发布 `0bc71c0`，落实后续任务第 1 项。CORS/可信代理、首次公网初始化授权和自定义 NULL 账号域名唯一性另起批次，不混入本次密钥修复。

## 启动顺序

1. 检查 Node 版本与数据库路径，不通过创建数据库来判断是否“首次安装”。
2. 选择 `AES_KEY` 环境变量或已有 `aes.key`；已有数据库缺两者立即拒绝启动。
3. 已有数据库以 **只读连接** 验证密文，先于 WAL/PRAGMA 写入、用户扩展 SQL 和迁移。
4. 初始化/验证统一 schema v5，再验证迁移/扩展后的密文与鉴权配置。
5. 创建或验证加密的内部启动校验记录；全部成功后才接受 HTTP 请求和领取后台任务。

错误输出不包含密钥、明文凭据或密文内容。错误 key 与损坏密文无法自动区分，均要求恢复原密钥或正确的数据备份；不会猜测密钥、跳过坏记录、重加密或删除数据。

## 文件与兼容策略

- 全新数据库才可自动生成随机 key，保持 `/data/aes.key` 默认路径。
- 先写完私有临时文件，再通过排他硬链接原子发布；不使用可能覆盖旧文件的 rename，也不暴露未写完的 `aes.key`。并发新安装读取同一个获胜 key。
- 已有 key 文件为空、无效 UTF-8、不可读、非普通文件或超过 64KiB 时失败，不覆盖该文件。
- 环境变量仍优先，但不把环境变量值自动写回文件。环境变量的长期可恢复性由部署方保证。
- 保留 `domain-hub.db`、旧 `dnshe.db` 与显式 `DB_PATH` 选择规则。主数据库缺失却存在 WAL/SHM/journal 时停止，不创建替代库。
- 旧库只有合法 `plain:`/历史明文设置时，显式提供 key 后仍可读取；“读取兼容”不等于可以在缺 key 时自动选择新 key。
- 没有既有 AES 密文或内部校验记录的 plain-only 旧库，无法证明某个 key 是它的历史 key。本次显式选择的 key 会建立校验记录，后续换 key 会被拒绝。
- 内部 `settings.node_aes_key_check` 保存的是标准 AES-GCM 校验密文，不保存原 key，不属于业务 JSON 备份。
- 没有新增表、索引或 schema 迁移；schema v5 与历史密文格式保持不变。

## 验证范围与就绪

启动按 24 行分批验证全部已有账号 Secret、活跃/待激活 2FA、加密通知配置、保留的 outbox 与恢复分片。不会只抽样验证第一条，也不会把坏 Blob 配置当作普通明文放行。

- `/healthz` 验证当前 schema、密钥校验记录、鉴权配置以及受管理的 key 文件；失败返回通用 503，不返回底层密文错误。
- `/livez` 只表示进程存活，不能替代就绪检查。
- 运行中 key 文件丢失/变化、启动校验记录被破坏时，进程可以仍存活，但不再报告就绪。
- 启动本身失败时没有 HTTP 监听、健康成功响应或同步/投递执行器。

只读 SQLite 参数自 Node 22.12.0 提供，因此最低版本提高到 **22.12.0**；现有 CI 的 Node 22 最新版本及 Docker Node 24 不变。README、包锁与 Compose 说明同步。

### 远端并发启动发现与修复

`d79f222` 的 Cloudflare 部署成功，但 CI 与 Docker 的共同验证在双进程启动用例失败：Linux/Node 22 出现只读预检数据库锁及切换 WAL 的 `database is locked`。这是实际启动竞态，不通过跳过测试处理。

- 可写连接在切换 WAL 前设置 `busy_timeout=5000`。
- 只读预检连接同样设置连接级有界锁等待；该 PRAGMA 不写数据库内容。
- 新增“持有短暂 EXCLUSIVE 锁后释放”的真实进程回归，验证会等待并正常校验，而非生成替代 key。
- 修复后专项测试 22 个通过，并发启动/短锁用例连续 10 轮通过。锁超时和密钥不匹配仍拒绝启动，不放宽加密策略。
- 补救提交前再次全量验证通过：**354 个用例**、workerd/Node 运行时冒烟、普通与自建前端构建均成功；Linux CI、Worker 部署和双架构 Docker 发布须由补救提交的远端工作流验收，不能沿用 `d79f222` 的结果。
- 补救提交 `82bf9e36aa72886cb93024714033c26b3b228b52` 已通过远端 CI（`44993155486`）、Cloudflare 部署（`44993155583`）、Docker 双架构容器冒烟与清单发布（`44993155498`）。线上首页与 `/api/auth/status` 均为 200，既有管理员/2FA 状态正常；没有进行生产密钥轮换或真实账号写入验收。

## 限制

- 保留的死信或 staging 密文损坏也会阻断启动；应在维护窗口恢复/明确处置坏数据，而不是为了启动随意删密文。
- 全量密文校验有与库存规模相关的启动成本，但读取内存有界；健康检查不重复解密全库。
- 不实现 key 轮换/双 key 迁移，原 key 必须与数据库/文件备份共同保存。
- 新安装的数据目录需支持安全硬链接发布；不支持时应显式提供 `AES_KEY`，不会降级为有覆盖风险的文件写法。
- Windows 文件权限依赖目录 ACL，不能将 POSIX `0600` 认作 Windows 的完整访问控制验收。
