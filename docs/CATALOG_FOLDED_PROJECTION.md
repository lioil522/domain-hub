# 固定时区下，按域名预先合并库存贡献

**决策：保留现有业务摘要。** 基于 `60cc281`，这次只比较隔离原型。50,000 个托管域名加 6,250 个自定义域名时，本地 workerd 的投影读取从 1.624 秒降到 1.144 秒，但现有业务代码完整生成冷摘要只需 0.374 秒；暖命中还可直接读取快照。这组数据不足以支持更改生产路径。

## 为什么可以提前合并

同一库存版本、源数据有效期和固定时区内，一个归一化域名只需保存：

- **原始过期条件**：任一有效来源的“已过期”标志，及最早的原始到期时间。Cloudflare 不贡献原始过期标志。到期比较仍在读取时使用严格的 `< now`。
- **解析后的到期日期**：取最早的有限日期，保留胜出来源的原始名称和账号别名。时间相同保留先到者。另记第一次遇到有限日期的位置，保证以后替换胜出来源时，同日时间轴条目的先后不变。
- **永久候选与注册信息**：永久候选只有在没有真实到期日、也未过期时才计数。注册用首次非空 `created_at` 的原值、来源和位置，独立于到期赢家。非法注册日期沿用旧比较器的完整候选回退。

构建时先按原来源顺序校验输入，使用请求内的 Map 归并。读取时仍重新计算到期、90 天预警和月份。V2 的 `catalog_prototype:2:` 命名空间与 V1 分开，保留相同的版本检查、五分钟/RDAP 源有效期、分片和整代字节上限。即使重复输入最终被合并，也计入源行和源字节准入预算。

V2 读端校验页数、字节、有效期、唯一的归一化域名、连续的存储位置，以及非空的首次到期/注册位置各自的唯一性和源范围。这里是结构与一致性校验，并非对派生数据的签名认证。固定时区和完整捕获是前提；到期字段极端到无法保证浮点 `daysLeft` 与整数毫秒排序等价时，原型明确拒绝构建。没有改动或删除源库存字段。

## 构建与读取一起比较

复现命令：`npm run benchmark:projection`。同一合成库存、固定业务时间、Node v24.15.0、Windows，每种规模及运行时重复三次，下表为墙钟中位数（毫秒）。`stage/read` 是上一轮的优化原型；`folded-stage/folded-read` 是本轮版本。两种格式各自完整捕获同一批输入，读端轮换执行顺序。两者均仅计算 `DashboardStats` 核心；现有业务冷摘要还计算其他元数据。

| 托管行 | 运行时 | 现有冷摘要 | 构建：逐来源 → 合并 | 读取：逐来源 → 合并 |
|---|---|---:|---:|---:|
| 1,000 | Node | 7.1 | 15.5 → 18.1 | 29.2 → 21.8 |
| 1,000 | workerd | 16.8 | 34.6 → 32.3 | 34.2 → 23.5 |
| 10,000 | Node | 64.2 | 134.6 → 159.7 | 329.4 → 244.6 |
| 10,000 | workerd | 84.5 | 240.0 → 207.2 | 301.4 → 215.5 |
| 50,000 | Node | 290.0 | 686.2 → 785.7 | 1,809.6 → 1,305.8 |
| 50,000 | workerd | 374.1 | 1,142.8 → 1,011.3 | 1,623.5 → 1,144.2 |

50k 组的两种原型都先读取 56,250 条库存和 523 条元数据。V2 保存 49,250 条合并记录，页面从 232 减至 197，JSON 总量从 30,123,286 减至 20,555,138 字节。workerd 模拟 D1 的读端 `rows_read` 从 2,510,335 降至 1,390,846（约 44.6%）；构建写入阶段报告的 `rows_written` 从 701 降至 596。后者不含源捕获，以上都不是生产账单。

Node 侧有真实的取舍：50k 构建多用约 100ms，单次读取少用约 504ms。workerd 的构建和读取都改善了，但即使不计构建，V2 读端仍是现有冷摘要耗时的约三倍。新 Map 也需要与唯一域名数成正比的构建内存；本轮未测峰值或生产计费 CPU。

## 结果对照与后续

18 次 V2 基准读取与现有摘要、两种 V1 读取的完整结果一致。原始报告在本机 Temp/opencode 的 `domain-hub-projection-performance-wHCqTC/report.json`。回归另覆盖跨来源重复、到期毫秒边界、月界、90 天进入点、版本/时区/期限、损坏的分片、非法日期、预算及空库存；workerd 冒烟使用同一代在较晚时间再读。

这个只保留赢家的格式适合测读端成本，**不是可持久更新的变更日志**：删除胜出来源时，仍需找回其他来源。建议在有真实只读成本数据，或能只重算受影响域名的方案之前结束这轮全量 JSON 投影实验。默认生产摘要、schema 和刷新协议均沿用既有实现。
