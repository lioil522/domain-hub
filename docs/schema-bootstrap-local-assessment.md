# Schema 自举本地优化：验证通过，云端 CPU 门槛仍未通过

2026-11-04 更新：用户已另行授权将此优化和日志表格修正提交、推送 GitHub，供 fork 用户部署；**本次不直接部署生产**。后续独立 staging 的 80 账号／560 域名迁移已按结构和数据正确性标准通过，旧数据、外键、序列保留；该验收不扩展为 CPU 达标保证。

以下为最初“本地优化（推荐）”阶段的历史诊断与限制。当时修改仅保留在隔离工作树，原 main 为 `0b1fb562f4062096aab3e12d61c05a81b74aeb7b`；已完成的原驱动、测试与停止证据保持不变。

## 改动与安全边界

- `src/db/database-manager.ts`：一次只读 batch 获取基础表清单及三组列信息；
  只跳过已存在的 11 张基础表的 CREATE，缺表和六种历史缺列仍补齐。
- `src/db/legacy-schema.ts`：提取原有 11 条建表定义，定义不变。
- 全部 22 条增量迁移（含索引、触发器、约束和 mutation clock 初始化）
  与缺表 CREATE／缺列 ALTER 合并为一次原子 batch，失败时一起回滚。
- 不增加持久化 schema-ready/version 标记；原始数据库身份缓存、失败关闭和
  后续调用重试保留。未改变 PBKDF2、AES、2FA、会话中间件或 40 D1／40 外部调用预算。
- 这不是任意损坏 schema 的完整审计器；保留原来的加法迁移职责，
  不用 IF NOT EXISTS 声称已经验证所有既有对象的定义。不同 isolate 的迁移竞争
  仍可能使某次调用失败关闭，需要后续新调用重试，不自动重放未知结果。

## 结构收益

80 账号／560 域名、11 张基础表且无需 ALTER 的 fixture：

| 条件 | 优化前 SQL／D1 调用 | 优化后 SQL／D1 调用 |
|---|---:|---:|
| 首次 `auth/status`（含迁移） | 37／6 | 27／3 |
| 已有 20 表但 schema 缓存未命中 | 37／6 | 27／3 |
| 缓存命中 `auth/status` | 1／1 | 1／1 |

空库的 schema 自举仍执行 37 条 SQL，合并为 2 次调用；完整首次 status
另加 1 条鉴权查询。节省 D1 调用次数不等于节省一半计费行数或 CPU。

- 新增 15 项 schema 单元回归和 3 项 workerd 回归；6 项相关 workerd 定向检查通过。
- Node 22.23.4／24.15.0 的 `npm run verify:all` 均通过：各 20 组、683 项
  不变量测试，失败／取消／跳过均为 0，另通过构建、类型、自托管测试及主题检查。
- 两版 Node 各通过 13 项隔离浏览器测试和 12 项隔离自托管 HTTP 检查。
- 前后对照完成 120 组 Node 试验、12 个新 workerd isolate／24 份 profile。
  本地迁移前后的完整旧表行哈希、序列和零 mutation clock 保留。
- 最初 CRLF／异步门禁 fixture 失败、Windows `--import` URL 驱动失败、
  日志解析格式问题均记录；没有将它们算成通过，也没有重跑已通过的一次性阶段。

## CPU 结论与限制

首次迁移的墙钟中位数：Node **2.109→2.044ms**，workerd **21.094→18.472ms**。
但 workerd 非空闲采样中位数为 **17.828→17.887ms**，未显示可靠下降。
已有 20 表时 workerd 墙钟为 **19.288→15.084ms**，非空闲采样为
**18.596→13.930ms**。这些仅为本地诊断，不是云端计费 CPU。

每条件／版本仅三个新 workerd isolate；采样稀疏，调试器和本地 D1 后端
不同于云端。重用同一 seed 时自动时间字段不同，不宣称云端完整行哈希相等。
历史首次迁移的 **11／12／15ms** 是独立样本，不是缩放或并发曲线。
**云端 15ms >10ms 的失败仍未解决，不能声称优化已满足 Free CPU 门槛。**
