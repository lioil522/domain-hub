# 降低持久同步快照的库存写入量

**适用范围**：`SyncWorkQueue.writeDomains()` 把 `sync_rows` 中已收齐的快照提交到 `domains_cache` 的阶段。Cloudflare 的逐页提交和旧的单行同步仍用原写入方式。本批没有新增表、索引、触发器或后台队列。

原 SQL 对每个冲突 ID 都更新 `account_id`、`expires_at`、`remote_id` 等列，即使有效值未变。`updated_at` 是库存行的观察时间，API 和备份会返回它。直接跳过整行会留下旧时间，因此新路径区分两种写入：

1. 新行照常插入；已有行只在将要赋予的业务值确实不同（NULL 安全比较）时做完整更新。上游未提供的凭据关联 ID、创建日期和 DNS 元数据仍按原规则保留；未知 DNS 不覆盖已知状态。
2. 对本次任务、当前账号的来源 ID 补写 `updated_at`，只列出这个非索引列。同一批在提交前从执行器取一个 UTC 秒值（格式仍为 `YYYY-MM-DD HH:mm:ss`），两条语句共用，避免跨秒时重复写刚更新的行。

库存更新、候选差集删除和游标仍在同一事务中，并共用同一个租约令牌／截止时间检查值。即使业务字段完全相同，仍完成同步并按既有规则更新库存版本、失效摘要。若主数据库在 `domains_cache` 上有自定义持久触发器，保留原来的完整更新及 SQLite 时间，避免改变 `UPDATE OF` 或观察次数。此兼容分支检查的是主库目录，不包括连接私有的 TEMP 触发器。

## 性能取舍

`npm run benchmark:snapshot-writes` 在独立内存库运行 Node/SQLite 和本地 Miniflare D1，对比基线 `2fb3b1a` 的写入 SQL。每次把库存时间设为过去，避免同秒重复运行造成“零写入”的假象。样本覆盖 100／1,000／10,000 行，每组 3 次。下表是 10,000 个已有域名且无自定义触发器时的本地 D1 中位数：

| 到期日变化比例 | 报告写入行（旧 → 新） | 报告读取行（旧 → 新） | 写入阶段墙钟 ms（旧 → 新） |
|---|---:|---:|---:|
| 0% | 60,000 → 10,000 | 60,001 → 80,190 | 114.9 → 57.7 |
| 10% | 60,000 → 15,000 | 60,001 → 82,190 | 110.2 → 68.8 |
| 100% | 60,000 → 60,000 | 60,001 → 100,128 | 115.4 → 134.1 |

主要收益在例行同步：业务数据不变时少写约 83%，10% 变化时少写 75%。如果全部变化，额外的比较和时间戳检查**只增加读取，没有写入节省**。因此不把该优化推广到页数小、输入特征不同的其他同步路径。

统计只覆盖库存写入语句。两组均通过版本包装器执行；其隐藏的版本写入、上游、暂存、差集和检查点不计入表中的读写行数。Node 适配器 `rows_read` 是占位，不能用于费用估算。这些测量不是生产 D1 账单或 Worker 计费 CPU。

运行 `npm run test:snapshot-writes` 可验证：与旧 SQL 逐字段对照、时间戳跨秒、保持未知 DNS 和空值语义、缓存失效、失去租约、检查点失败回滚及持久触发器兼容。workerd/D1 冒烟另用隔离库实际执行队列写入和检查点提交。
