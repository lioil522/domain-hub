# 脏键表与追加日志：隔离对照

基于 `f688231`。**不启用生产变更捕获、不增加正式数据库表、不改摘要或刷新协议。** 运行 `npm run test:prototype:catalog` 执行回归，运行 `npm run benchmark:dirty-keys` 复现实验。原 `benchmark:capture` 仍用于变更日志和依赖索引的对照。

## 保留哪些键

同一业务事务内，变更触发器把 `(类型, 键)` 写入隔离表。库存变更保留源表 ID 与旧、新原始域名；手动覆盖和 RDAP 变更保留旧、新日期键；账号变更保留账号 ID。改名再删除时，不能只保留最后的名字，也不能把不同类型的同名键混在一起。归一化和候选依赖仍由共享 JS 在消费侧解析。表里没有凭据、缓存值或完整事件顺序。

已有待处理键不重写；被领取的键再次变脏时清除领取标记。领取使用新的随机令牌，最多 256 个键，有效期 30 秒；仅匹配当前令牌且尚未到期的确认才能删除键。回归验证了重领、超时、删除后重建，以及事务回滚不会破坏原领取。这里只保护**确认删除**，并不防止过期执行者发布旧计算结果；生产需要把结果发布也纳入同一版本检查。

## 本地测量

Node SQLite 和本地 Miniflare D1 分别用独立内存库测 100、1,000、10,000 条模拟库存。每个阶段排空后再运行下一阶段；比较两种方案读取的原始键集合摘要，而不是假定记录数相等。混合同步使用真实批量 UPSERT 辅助函数和差集删除；热点组在一个事务内更改同 20 条记录 25 次；最后删除托管账号。

下表为 10,000 行组，写入数取本地 D1 的 `rows_written`，**不是生产账单**。总写入包含两边相同的业务写入、捕获和清理；脏键表另计领取写入。追加日志只模拟单消费者静态排空，不含与脏键表等价的并发领取或持久位点。

| 场景 | 待处理行：追加 / 去重 | 捕获阶段写入：追加 / 去重 | 领取与清理：追加 / 去重 | 合计：追加 / 去重 |
|---|---:|---:|---:|---:|
| 混合同步，域名大多唯一 | 3,000 / 6,000 | 64,002 / 67,000 | 3,000 / 12,000 | 67,002 / 79,000 |
| 热点重复修改 | 500 / 40 | 2,025 / 1,540 | 500 / 80 | 2,525 / 1,620 |
| 账号级联删除 | 10,002 / 20,002 | 20,005 / 30,004 | 10,002 / 40,004 | 30,007 / 70,008 |

热点场景总写入减少约 36%；混合同步增加约 18%；级联删除约为追加日志的 2.33 倍。单条日志可携带多个键，而去重表要为每种键单独留行，因此**不推荐用这版去重表全面替换追加日志**。节点适配器的直接变更计数不能代替 D1 对隐式写入的报告。全量排空由本地测试驱动跨多次查询完成，不代表单次 Worker 调用能处理全部工作。结果没有计入索引修复、最终摘要发布、查询读取、生产账单或延迟。

## 未解决

隐式 `REPLACE` 删除、RDAP 自然到期和捕获以外的写入仍与前一实验有相同限制。尚未实现公平调度、结果发布与确认原子化、生产消费者或跨版本迁移。若继续，只在有实测的热点工作负载下评估消费端批内归并；不要把去重写入的收益外推到级联删除。
