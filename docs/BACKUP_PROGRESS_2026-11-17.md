# 第四批：备份恢复的安全边界与真实预览

> 本文记录修复阶段状态；“未提交/推送/部署”指当时。后续主分支发布范围见[发布说明](./RELEASE_NOTES_2026-11-17.md)。

以下记录第四批当时的范围；后续分段恢复已在[第五批记录](./STAGED_RESTORE_PROGRESS_2026-11-17.md)中实现，仍不支持自动 ID 映射。

处理 P1-18 的格式、密钥、冲突安全边界及 P1-19 的导入后刷新。本批未提交、推送或部署；没有访问生产数据。**分段恢复与自动 ID 映射尚未实现，不能把本批当作整个备份路线已完成。**

## 已实现

### 格式、密钥及完整性

- 导出仍仅包含 5 张业务表，不包括登录配置、2FA、会话、作业状态、日志或临时缓存；它不是完整灾备。
- 导出在一个读事务中获取数据，使用显式业务列，不夹带数据库操作者添加的其他列。
- 格式版本仍为 1；新快照增加 metadata：business scope、schema_version、AES_KEY 指纹及 SHA-256 checksum。
- checksum 使用稳定 JSON 排序，覆盖数据、行数、导出时间和元数据；读取时验证行数及校验和。
- **checksum 只能发现损坏/改动，不是签名，不证明文件来自可信来源。** 操作者仍需保护备份和 AES_KEY。
- 同步校验所有行的类型、必要字段、整数 ID、服务商和引用；不再将对象强制转换为字符串或静默跳过无效行。
- 兼容旧版无 metadata 的 v1 快照，但逐账号验证实际密文能否用目标 AES_KEY 解密。
- 新格式 key 指纹不匹配、密文无法解密、格式损坏均在业务写入前拒绝；不能通过生成新密钥“修复”旧密文。
- 历史 plain: 凭据在导出/导入时升级为 AES 密文，不新增弱编码凭据。仅检查解密，不调用上游验证 API Key 是否仍有效。
- API 对数据请求设置 20MB body 上限。

### 冲突预览与事务保护

- 相同数字 ID、不同业务身份不能覆盖；同一自然身份使用另一 ID 时明确要求映射，不擅自改 ID。
- 检查 API Key 全局唯一性、账号/分组引用、手动账号的分组归属，以及域名显示身份和远端身份。
- 输入自身的重复 ID、重复业务身份及目标库已有 nullable 手动域名重复均显示为冲突。
- 预览返回真实新增、更新、目标独有行及冲突数，并包含最多 50 条安全错误说明；不返回账号 Secret。
- 目标独有行的 remove 数仅作差异提示，不执行删除。
- 实际导入重新校验，不将先前预览当作授权绕过；SQL 内部的身份 fence 防止检查后又出现 ID/自然键碰撞。
- 身份碰撞中止整批事务，不能提交其他兄弟行，也不能删除并发操作者刚写入的记录。
- 相同 ID 且身份一致的备注、日期等字段仍可合并覆盖。**没有实现字段级三方合并或所有字段变动的乐观锁。**
- 数据已经提交、后续审计失败时返回成功与警告，不误报“导入失败”诱导再次提交。

### 前端

- 流程变为“选择文件 → 验证并预览 → 核对数量/冲突 → 确认合并导入”。
- 冲突或超过上限时禁用确认；旧文件读取/预览结果不能覆盖更新后的选择。
- 下载快照保留完整性元数据。
- 导入后刷新账号、DNSHE、其他 API 服务商、自定义域名和配额派生状态。
- 列表刷新失败与数据导入失败分开提示；修正“备份可能覆盖 2FA”的错误注释和界面文案。

## 限制及下一步

当前仍保留 **500 行的应用上限**，不会直接改成更大的 batch。Workers 的实际 D1 请求/事务预算还受计划及调用路径限制，不能据此承诺每种环境都能单次写满 500 行。

下一批大快照方案应满足：

1. 创建持久 restore session，保存快照摘要、schema/key 指纹、操作者范围、有效期与状态。
2. 以小块上传 staging；每块有序号和摘要，重复提交幂等，业务表保持不变。
3. 逐批校验全局重复、引用和自然键，生成显式 ID 映射及人工确认的覆盖计划。
4. 最终提交采用有界 set-based SQL 与事务，不将全部行扩为单请求无限语句。
5. 任何 staging 中断、校验失败或提交失败，不留下部分业务恢复；会话能恢复、取消、过期清理。
6. 测试超过 500/10,000 行、跨账号 ID 冲突、并发变更、不同密钥、重复 chunk 和最终提交回滚。

完整灾备仍需数据库文件/平台恢复能力与原 AES_KEY；目前 JSON 业务快照不包含密码和 2FA，不能替代这些备份。
